有时，最有用的修改是一段终于不必维护的代码。

最近整理一个小项目时，我删掉了一个很早以前写下的抽象。那时的想法并不复杂：既然以后可能出现第二种需求，不如现在就把位置留出来。

可第二种需求一直没有出现。留下来的反而是解释成本：为什么这里要绕一层，这个配置究竟由谁负责，改动的时候到底要同时看几个地方。

## 先把现在的事情说清楚

我开始试着给每一块代码写一句很短的说明，不谈设计模式，只说它现在替谁做什么。如果一句话里面连续出现几个“以及”，就把职责再看一遍。

> 能被清楚解释的边界，通常也比较容易修改。

这不是追求最少的代码。有些重复值得保留，有些公共逻辑确实应该放在一起。区别在于，决定来自已经存在的变化，还是来自对未知变化的想象。

对一个个人网站来说，文章不必知道地图怎样画出来，地图也不必决定文章如何组织。它们只需要在需要的时候，拿到同一份确定的信息。

## 把变化留在外面

外面的颜色、动画、布局，可以不断试。里面的文章和地点关系，则尽量保持普通。漂亮的效果有一天会过时，但一篇文章不应该因为换了效果就要重新写。

删除结束以后，项目没有多出任何新功能。我只是更愿意打开它了。这大概也是一种很实际的进展。

const published = articles.filter((article) => !article.draft);
