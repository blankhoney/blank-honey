问答能显示以后，接下来想知道两件事：改代码有没有弄坏接口，生成内容为什么会这样。这两件事需要看的材料不同。前者可以给固定输入检查字段，后者得展开 query、召回和 prompt，沿这次请求往回找。

## 看一次实际回答时，往哪里翻

如果报告偏题，我会先展开改写后的 query，确认它还在问原来的事情；接着看召回片段，再看生成节点实际拼进去的上下文。这是排查顺序，不是某次故障记录。例如证据在 bundle 里，却被截断在 prompt 外，光看检索返回成功就会漏掉问题。

LangSmith 可以记录这些调用。[自定义追踪](https://docs.langchain.com/langsmith/annotate-code)需要接在实际经过的函数上，新接口或新异步路径也得重新确认覆盖。仅安装 SDK，不能保证后来新增的聊天入口都会出现在预期的 trace 中。

固定输入的测试用来检查另外一层约定。九月整理的 `test_retrieve_structure.py` 只验证召回结果的必要字段，judge 测试只验证 JSON 解析与回退。它们没调用真实检索与模型，也没覆盖完整 B 循环；实际输出的缺口仍要沿上面的 trace 查。

文档这阶段整理了 README、`DEMO_CHECKLIST` 和 `INTERVIEW`。启动步骤、演示前检查与选型说明各放各的位置，免得现场讲到一半才去找配置。检查 README 时，适合在一个新目录按顺序走：旧目录里的缓存和已生成文件，常常会让漏写的步骤暂时不报错。

`eval_smoke.py` 留给典型输入的快速演示检查，看看追问、报告结构与引用有没有明显异常。它不是带完整样本和指标的医学评测。发现某条输出不对，就带着这条输入找对应过程记录；字段缺失先改代码，材料不对先查召回，报告漏读再看 prompt，不把所有失败都归给模型。
