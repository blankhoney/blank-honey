一直用 curl 讲 `/v1/dual`，开头总得先展开 JSON，解释哪个字段是追问、哪个字段是报告。内容还没开始读，已经花了一段时间认字段。所以这一阶段做个小页面，把两份输出直接放到对应位置。

左边放用户消息与 A 线追问，右边放 B 线的阶段性报告。输入区留在对话旁边，处理状态单独显示。报告里的引用也跟着内容放，讲解时可以沿着一句话回头找资料，不用再切到响应文本里翻字段。

```text
┌──────────────┬────────────────┐
│ 用户消息     │ 阶段性报告     │
│ A 线追问     │ 引用与待补信息 │
│              │                │
│ 输入与发送   │ 处理状态       │
└──────────────┴────────────────┘
```

这是布局示意，不是当时截图。同步接口还要等 A/B 一起完成，发送后得告诉用户正在处理，并挡住重复提交。否则一段没有反馈的等待，很容易变成多点几次按钮。

技术上用 Vite + React。这个页面不需要 SEO 或复杂路由，先把状态放在 `App.tsx`，CSS 也直接写。此时比起搭一个组件体系，我更想打开一个文件就能看到：请求从哪里发出，返回后哪一块更新，失败时输入还能不能继续。

会话标识 `session_id` 放在 localStorage。刷新后用它向后端读取会话，完整消息没有只靠浏览器保存。这里没有账号体系，这个 id 负责把请求接到同一段对话，不能把它当成登录凭据或病历身份。[localStorage 的行为](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)也按浏览器与来源保存，不会自动替我们解决跨设备会话。

后面加流式输出和异步报告时，两边会有不同的完成时点。布局先分开，状态也要分开：对话正在输出，不等于报告正在生成；报告失败，也不应该把已有聊天全部清空。九月整理时页面已经有这些后续状态，不能用当前页面反推三月每项都已具备。
