检索接口先留一个 mode。同一个问题可以跑 hybrid，也可以跑 graphrag，生成节点接到的统一叫 `recall_bundle`。我想先在生成前停一下，把返回材料读明白，再看模型怎样使用它。

hybrid 用 Qdrant 和 BM25 查同一批 Markdown 片段；图侧使用 Neo4j 的实体与关系。一次请求选一种模式，没有把两路全部查完再融合。这样切换后，哪一条材料来自哪条路径比较容易看，也不用让每次演示都等两套检索。

九月整理现存的 `backend/adapters/retrieve.py` 时，hybrid 的合并方式可以具体算出来。两路各自排序，再按名次加分，代码里的贡献是 `1 / (60 + rank)`。同一个 chunk 在两边出现，贡献就相加；只出现一路，也保留那一路的分数。

```text
说明例：chunk A
Qdrant 排第 1：1 / 61
BM25 排第 3：  1 / 63
合并分约为 0.03227
```

它没有直接把向量相似度和 BM25 原分数加起来。排位贡献可以解释为什么两边都找到了的片段会往前走，不过也要检查两路的 id 是否能对上。现在 BM25 的分词还是按非空字符拆分，看到“关键词检索”几个字，不能想当然地以为已经做了复杂中文分词。

图侧也比较朴素。当前实现先找问题里包含名字的实体，再取它相邻的一条关系；找不到时，按名称和描述里的关键词匹配。返回的实体名、关系和说明被拼成文本。这是项目中名为 graphrag 的检索路线，还没有实现任意多跳路径规划，也没有复现微软 GraphRAG 的社区摘要流程。

上层收到的片段有 id、text、score、source、mode、metadata，库各自的原始返回留在 adapter 内部。生成前查看这几个字段，就可以知道正文是否完整、来源从哪来。若某个关系根本没导进图里，切换接口不会替它补上；同一个问题两边表现不同，也可能是资料覆盖不同。

我暂时保留两条独立入口。以后要融合，得先决定重复片段怎么合、失败的一路怎么处理，再评估多查一套库值不值。
